# V41.0 — 对齐器阶梯的容量-泄漏双重审计

> **日期**: 2026-10-10
> **状态**: ✅ Verified (8/8 单元测试 PASS, 6 臂 × 5 seeds = 30 run)
> **复现命令**: `python3 examples/run_v41_capacity_audit.py` (CPU 约 11 分钟)
> **审计对象**: v13 的对齐器阶梯主张,以及 **E2** 这个自 v14 起挂账的未闭项
> **一句话**: **E2 结清 —— 容量混杂被排除。** 在参数量**严格相等**的条件下,
> mixture 比 attn 好 **36.5%**,5/5 配对种子全胜。

---

## 1. 动机:一个挂了两年的未闭项

`docs` 记录的对齐器阶梯:

| 级别 | 对齐器 | fuse MSE | 参数量 | 容量序 |
|---|---|---:|---:|---|
| 1 | linear `P_m` (v6/v7) | 1.0436 | 325,632 | 1.00× |
| 2 | attn (v10) | 0.3448 | 720,640 | 2.21× |
| 3 | **mixture (v13)** | **0.2575** | 2,291,968 | **7.04×** |
| 4 | mom (v15) | 0.2645 | 1,704,448 | 5.23× |

**性能序与容量序完全一致。** 因此"阶梯在爬升"这件事既可以读成"对齐器设计逐级更好",
也可以读成"参数量逐级变大"——**两者在现有数据里不可分辨**。

这就是 E2:*「阶梯规模化 + 容量匹配对照」*,自 v14 写进 SPEC 之后一直没做。
论文 `microfusion.tex` 也把它列为未闭项。

## 2. 关键构造:一个精确等容量对

要解开"设计 vs 规模",需要一组**参数量严格相等**的异构机制。这不是调参能凑出来的,
但它是**构造出来的**:

```
MixtureAligner 的专家部分 = n · Σ_m (D_m·d + d + d² + d)
                           + 2d² + (d² + d)        ← W_k + W_v + out_proj
  d = 256, (D_bert, D_llama, D_vit) = (312, 768, 192)
  → 每专家 523,776,  固定部分 196,864

n = 1 → 720,640
n = 2 → 1,244,416
n = 4 → 2,291,968
n = 8 → 4,387,072

CrossArchAttnAligner = 720,640      ← 与 n=1 **完全相等**
```

`attn` 与 `mixture-n1` 因此构成**逐位相等的等容量对**。单元测试
`test_capacity_matched_pair_is_exact` 把这条性质锁死,解析式也与实例化逐位一致。

### 一个必须讲清的测量口径

参数量只数**对齐器**。`AlignedFusionLayer` 自带的
`gammas / betas / alphas / W_router` 共 **266,246** 个可训练参数**各臂完全相同**,
数进去会把等容量对淹没在共享项里(早期版本正是这么错的,导致 attn 显示为 986,886)。

## 3. 结果

held-out = `prepare_data(base_seed + 1000)`,**同分布、不同抽样**(只换噪声与图像抽样)。

| arm | 对齐器参数 | 相对 attn | in-sample 中位数 | **held-out 中位数** | 泛化落差 |
|---|---|---:|---:|---:|---:|
| attn | 720,640 | 1.00× | 0.3813 | **0.3952** | **+4.6%** |
| mixture-n1 | 720,640 | **1.00×** | 0.2379 | **0.2422** | +0.2% |
| mixture-n2 | 1,244,416 | 1.73× | 0.2957 | 0.2964 | +0.3% |
| mom | 1,704,448 | 2.37× | 0.3115 | 0.3115 | −0.0% |
| mixture-n4 | 2,291,968 | 3.18× | 0.2407 | 0.2405 | +0.6% |
| mixture-n8 | 4,387,072 | 6.09× | 0.2554 | 0.2557 | +0.1% |

### 3.1 E2 裁决:容量混杂被排除

等容量对(720,640 ≡ 720,640):

| 口径 | attn | mixture-n1 | mixture 优 |
|---|---:|---:|---:|
| held-out **中位数** | 0.3952 | **0.2422** | **+36.5%** |
| held-out 均值 | 0.3797 | 0.2583 | +28.8% |
| 配对逐 seed | — | — | `+25.5 / +3.3 / +40.4 / +27.1 / +42.6` |
| 去掉最好的 seed 后(中位数) | — | — | **+33.5%** |

**5/5 配对种子全胜。** 结论对统计口径不敏感(中位数/均值/配对/去最好种子,四种口径同向)。

> **容量完全相同,机制不同,差距 36.5%** ⇒ attn → mixture 的增益来自
> **"所有底座的专家放进同一个池子"这一机制**,不是来自"参数更多"。
> **E2 结清。对齐器阶梯作为 main finding 成立。**

### 3.2 容量曲线是平的

沿 mixture 家族扫容量(1× → 6.09×),held-out 中位数:
**0.2422 → 0.2964 → 0.2405 → 0.2557**。

容量翻 6 倍只换来 −5.6%,而且**非单调**(n2 反而差于 n1)。

> 这是 E2 担心的另一半:"阶梯读的是规模"。现在可以正面否定 ——
> **规模在 `n_shared_experts=1` 之后基本不再产生收益。**

**诚实限定**:该曲线受种子方差支配(单臂 5 seed 范围可达 0.22–0.31),
非单调很可能是噪声而非真实趋势。结论只取"**无单调上升趋势**"这一定性判断。

### 3.3 v15 嵌套天花板也不是容量造成的

`mom` 容量是 `mixture-n1` 的 **2.37×**,held-out 中位数反而**差 28.6%**(0.3115 vs 0.2422)。

> 嵌套退化是**架构表达力**问题,与规模无关 ——
> 这与 v39 对加性融合头的构造性证明(XOR 无加性分解)同族:
> **接口的组合方式决定上限,接口的宽度不决定上限。**

### 3.4 泄漏:v13 的 in-sample 评估

`v13` 的 `eval_teacher` 在**训练同源数据**上评估。本代对每个臂同时报两个口径。

| arm | 泛化落差 |
|---|---:|
| **attn** | **+4.6%** |
| mixture-n1 / n2 / n4 / n8 | +0.2% / +0.3% / +0.6% / +0.1% |
| mom | −0.0% |

attn 是唯一有实质落差的臂。但要注意方向:**attn 的 in-sample 本身也差**(0.3813 vs 0.2379),
所以不是"in-sample 好看、held-out 穿帮",而是 **attn 两头都差**。

> **对齐器阶梯的主张在 held-out 上依然成立**,泄漏审计结论 **clean**。

## 4. 局限(诚实边界)

- 只审**对齐器阶梯**。学生蒸馏线的 +47.5%(v16,已被 v32 推翻)与
  多模态线的 **+50.5%(v21)不在本代范围**。
- 臂间只做 **seed 对齐**,不做 `state_dict` 对齐(架构不同无法共享)。结论依赖**配对**而非同初始化。
- 全部在 CPU 沙箱:`D_shared=256`,序列长 16,合成 class-direction 目标。
- 5 seeds 对该指标偏少(单臂范围 0.22–0.31)。E2 的结论因 5/5 配对全胜而稳健,
  但容量曲线的细节不稳健。
- `mixture-n1` 与 `mixture-n4` 在本协议下性能几乎相同(0.2422 vs 0.2405)。
  docs 里 v13 用的是 n=4;**n=1 以 1/3 容量达到同等性能**,这一点本身值得后续关注。
